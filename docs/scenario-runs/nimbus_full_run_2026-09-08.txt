6. WHAT DID NOT COMPLETE THIS RUN, AND WHY (root-caused, not guessed)
----------------------------------------------------------------------------------------------------
48 of 51 scenario checks passed. The 3 failures trace to ONE root event, so this
section explains that event precisely rather than restating the check list.

Fatima Noor (WhatsApp) completed her interview normally: 4 real discovery turns,
closed on 'stalled' (not 'dossier_complete') after floor (4) was reached. Every
turn's insight/summary was genuinely on-topic and correct (see section 2 above) —
but the structured 'slots_filled' field the model is asked to report alongside
its reply came back empty on all 4 turns, so the dossier never marked
'how_it_works' or 'friction' as filled even though her answers plainly covered
both (turn 3: "Checking the PI is fully manual — I compare it line by line";
turn 4: "About one in four PIs has a mismatch"). Both branch-phase turns asked
for the SAME slot (how_it_works on LPO management) because nothing ever registered
as filled, so the orchestrator kept re-asking it until the stall counter closed the
interview. This is a MODEL reporting-fidelity gap (correct prose, empty structured
field), not a routing bug — the beat/slot_hint the model was given each turn was
correct per the message log's routing_decision. Net effect: BuildPackageService
still produced a good package (it also reads the raw per-turn insights and parked
asides, not only dossier.slots), so the pipeline was resilient to this — but a
'complete' interview closed for the wrong reason and the report's readiness
arithmetic never saw a filled dossier for her.

Sara Haddad (web) did not complete. Her first two turns (orient phase) were quick
(16s and 1m22s). Her THIRD turn — the first branch-phase question, on 'Order
Confirmation' / 'Procurement Handover' — never returned: the call ran for the
full LANGGRAPH_READ_TIMEOUT (1800s / 30 minutes) before the HTTP client gave up.
Discovery::ProcessTurnService caught that as a retryable Langgraph::UnavailableError,
tripped the shared OpenAI circuit breaker, and returned a delay message. Every
scripted answer the scenario sent immediately afterward hit that now-open breaker
instantly (see the run of 'delay_notice' replies, all timestamped 12:50:26) — by
design, an ALREADY-open breaker is not re-tripped and is not retried synchronously,
so the conversation stayed stuck at question_count=2 for the rest of the scenario's
MAX_DISCOVERY_TURNS budget. A background retry job was scheduled 30s after the
original failure, but the scenario script does not wait for it, so it never had a
chance to let the conversation catch up before the run moved on.

Consequence for intelligence: SignalExtractor only reads messages from COMPLETED
conversations, so Sara's 6 real (but never-graded) answers contributed NOTHING to
signals/patterns despite being genuinely on-topic (CRM/Excel re-entry, no linkage
between sales order and LPO, stale customer quotes). The 6 signals and 3 patterns
reported above come from Fatima's interview and the 4 documents ONLY.

This is a known, previously-documented characteristic of this local Gemma
configuration under sustained multi-turn load (branch-phase turns are measured at
roughly 5,700-6,000 reasoning tokens vs ~800 for orient-phase turns, and local
throughput degrades further the longer LM Studio has been running back-to-back
calls) — not a regression introduced by anything in this branch. A GPT-4.1-mini
run of the same scenario completes both interviews in a few minutes total with
dossier_complete firing normally; this run intentionally used the local model per
the current .env, which is the right choice for a zero-cost full-pipeline proof but
the wrong choice when interview quality (not just pipeline plumbing) is what's
being evaluated.
